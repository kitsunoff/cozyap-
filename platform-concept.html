Центральный конфликт

Обобщённость против хорошего UX

Модель, достаточно общая для игрового сервера, обычно слишком абстрактна, чтобы дать Java-разработчику хорошую форму. Модель под twelve-factor не потянет WordPress. Все runtime-PaaS из исследования решили это, отказавшись от общности. Нам нельзя.

Единый контракт, множественные реализации, курируемое отображение.
Каждый кирпичик соблюдает один контракт: типизированные порты, готовность, статус, billing-метаданные, facets. Как он реализован — своё у каждого типа и невидимо для графа. Что видит пользователь — заготовку из каталога, а не сырую модель.

Это же снимает противоречие между V1 («всё — кирпичик») и границей ADR-0019 («ядро — свой контроллер, зависимости — Crossplane»). Граница выживает как свойство конкретных типов кирпичиков, а не как раскол модели.

Пять слоёв

Слой 1 множественный намеренно. Слои 2–5 единственные — на них построен весь продукт.

Слой 2

BrickDefinition — тип кирпичика

kind: BrickDefinition
spec:
  type: core.cozyap.io/PostgresDatabase
  parameters:            # OpenAPI-схема → сгенерированная форма
    size: {enum: [small, medium, large]}
  ports:
    out: [{name: connection, type: core.cozyap.io/sql}]

  implementations:      # одна и та же семантика, разные реализации
    - match: {targetClass: cozystack} → Composition xpostgres-cozystack
    - match: {targetClass: aws}       → Composition xpostgres-rds

  targetRequirements:  # что доставить в дата-плейн, с refcount
    - {package: cnpg-operator, version: ">=1.24", scope: dataplane}

  acceptsTraits: [backup, monitoring, resource-limits]
  facets: [{kind: link, name: Grafana, urlTemplate: "..."}]
  billing: {unit: instance-hour, dimensions: [size, storageGiB]}
  ui: {descriptor: ..., plugin: {image: "registry/.../pg-ui:1.4.2"}}

implementations

Идея Radius. Один контракт, несколько реализаций, выбор по тому, куда приземляется. Это V7 в одном поле.

ports

Типизированный выходной контракт. Без него рёбра не типизируются, и редактор — рисовалка.

facets

Вклад в отображение, при котором UI не знает о существовании кирпичика.

Слой 3

Порты — закрытый список типов

Добавление типа порта — релиз платформы. Добавление кирпичика — нет. Это и есть точка, где модульность упирается в стабильность.

Источник

git-source
oci-image

Данные

sql · redis
queue · s3-bucket

Сеть

http-endpoint · k8s-service
tls-cert · dns-name

Прочее

secret · config · target
openapi-spec · docs-site

Правило графа: топология выводится из spec.connections между инстансами — как kro строит DAG из CEL-ссылок. Хранить граф отдельно значит завести второй источник правды, который разъедется при первом же kubectl.
Слой 3

Connection делает три вещи

1

Поток данных

Выходы продюсера становятся входами консьюмера. Очевидная часть.

2

Инъекция

Env-переменные и смонтированные файлы, разрешаемые в момент деплоя. Требование R3 — никакого ручного переноса паролей.

3

Авторизация

Создание связи — это то, что создаёт пользователя БД, политику бакета, IAM-биндинг. Про это забывают.

connections:
  - name: db
    from: {instance: api-db, port: connection}
    inject:
      env:   {prefix: DATABASE_}      # DATABASE_HOST, DATABASE_PASSWORD…
      files: {path: /bindings/db}     # форма Service Binding
Из-за пункта 3 связь не может быть «просто лейблом». И поэтому в UI ребро обязано показывать, какой доступ оно выдаёт — иначе мы приучаем людей раздавать права не глядя.
Слой 4

Application — тонкий агрегат, плюс Release

kind: Application
spec:
  blueprintRef: {name: java-service, version: 2.1.0}
  selector: {matchLabels: {app.cozyap.io/application: payments-api}}

Он не владеет кирпичиками. Он их выбирает. Следствия — все желаемые:

  • ресурс, созданный вне платформы, усыновляется простым проставлением лейбла;
  • RBAC и статус — на уровне инстанса, а не одним грубым блобом;
  • графовый редактор работает с реальными объектами, а не с секцией большого CR.
Release закрывает откат (дыра G1). Неизменяемый снимок разрешённых входов: digest образа, коммит, версия заготовки, все параметры. Откат = «сделать релиз N активным».
Что релиз не откатывает — миграции схемы БД. Это надо говорить пользователю в интерфейсе, а не только в документации.
Читаемость

Кирпичик · Trait · Facet

Узел графа

Brick

Есть выход, который потребляет другой кирпичик.

Build, PostgresDatabase, HttpRoute

Бейдж на узле

Trait

Меняет поведение одного кирпичика и только его.

autoscaling, backup, network-policy, sidecar, pdb

Боковая панель

Facet

Вклад в отображение приложения.

link, metric, panel, action, health, badge

Правило для линтера: есть выход, который кто-то потребляет → кирпичик. Меняет поведение одного кирпичика → trait. Без этого правила Java-сервис из шести кирпичиков рисуется двадцатью узлами и его перестают читать.
Каталог

Кирпичики — первый срез

Источник и SCM

GitSource · GitRepository · SourceTrigger · PipelineGenerator — пишет CI-конфиг в репо, чтобы платформа потом видела образ

Сборка и образ

Build (kpack) · DockerfileBuild · ImageRef · ImagePolicy — следит за новыми тегами в реестре

Workload

Workload · StatefulWorkload · HelmWorkload · VirtualMachine · ScheduledWorkload

Зависимости

PostgresDatabase · MySQLDatabase · RedisCache · MessageQueue · ObjectBucket · ClickHouseDatabase

Сеть

HttpRoute · Certificate · DnsRecord · L4Endpoint — UDP/TCP, без него CS2 не выразить

Платформенные и мета

ObservabilityBinding · SecretStore · OpenApiSpec · DocsSite · ExternalResource

ImageRef и ExternalResource — не мелочь. Первый делает приложение без стадии сборки нормальным случаем, а не исключением. Второй делает усыновление чужого ресурса частью модели.
Сервисные ресурсы

Про PythonEval: это два разных примитива

Не нужен ресурс

Чистое вычисление

Вывести значение, переформатировать параметры, посчитать имя — это рендер. В Crossplane уже есть function-python с полной стандартной библиотекой, плюс function-kcl и function-kro.

Отдельный CR тут строго хуже: лишний объект, лишний reconcile, лишний режим отказа и никакого сандбокса.

Нужен ресурс

Работа с побочным эффектом

Дёрнуть внешний API, прогнать миграцию, отскаффолдить репозиторий, снять бэкап — нужен свой жизненный цикл, retry, таймаут, логи, ключ идемпотентности и статус.

Этого у Crossplane нет. Форма правильная у Kratix — упорядоченные контейнеры.

kind: Task            # PythonEval — это профиль Task, а не отдельная концепция
spec:
  runtime: {python: {inline: "...", requirements: [requests==2.32.*]}}
  idempotencyKey: "{{ .spec.inputs.hash }}"
  policy: {timeout: 15m, retries: {limit: 3, backoff: exponential}}
  placement: platform      # никогда в дата-плейн — ограничение V6
Безопасность

Inline-код в CR — это RCE с YAML-фасадом

Это приемлемо. Но только со всем нижеперечисленным, и в v1, а не в «потом захардним».

1

Исполняется в плоскости платформы, никогда в дата-плейне. Это же разница между «задачей» и «плацдармом в кластере тенанта».

2

Отдельный минимальный ServiceAccount на задачу, ограниченный тем, что объявил кирпичик. Не идентичность платформы.

3

Явный RBAC на создание задач с inline-кодом. Разработчик, заполняющий форму, не должен мочь. Автор пакета и оператор — могут. Код из заготовки — отревьюенный контент, код от пользователя — эскалация.

4

NetworkPolicy default-deny, egress только объявленный.

5

Лимиты и жёсткий таймаут всегда. Никаких безлимитных дефолтов.

6

Никакого разрешения зависимостей в рантайме. requirements резолвятся при сборке пакета. Задача, которая делает pip install на старте, — это и дыра в цепочке поставок, и флак.

Если хоть один пункт кажется настолько неудобным, что хочется пропустить, — честный ответ поставить работу образом в пакете, а не inline-кодом.
V7

Target — Cozystack как один из провайдеров

kind: Target
spec:
  class: cozystack | kubeconfig | cloud   # по этому матчатся implementations
  capabilities: [ingress, loadbalancer-l4, block-storage, gpu]
  defaults: {observability: platform-stack, secretStore: openbao-prod}

class

То, по чему BrickDefinition.implementations выбирает реализацию. Cozystack становится провайдером, а не платформой.

capabilities

Линтер заготовки отклоняет приложение до деплоя: заготовка CS2 требует loadbalancer-l4 и не поедет на таргет без него.

Падать на этапе авторства, а не на этапе деплоя — это и есть разница между платформой и кучей контроллеров.
V6

Чистые дата-плейны и refcount

Позиция по умолчанию: в дата-плейне крутятся только рабочие нагрузки. Ни Crossplane, ни оператор платформы, ни раннер задач. Реконсиляция, композиция и задачи исполняются в плоскости платформы и действуют на дата-плейн через ограниченный креденшл.

targetRequirements:
  - {package: cnpg-operator, version: ">=1.24", scope: dataplane}

По требованию

Платформа ставит машинерию, только когда её реально запросил кирпичик.

Refcount

Оператор снимается, когда исчез последний кирпичик, который его требовал. Это неочевидная часть — два приложения делят оператор, одно удалили, второе не должно сломаться.

Конфликт версий

Два кирпичика с несовместимыми требованиями к одному оператору на одном таргете — отказ на этапе авторства, а не сюрприз в рантайме.

Редактор

Два продукта на одном канвасе

Редактор заготовокВид приложения
РедактируетApplicationBlueprint — шаблонЖивые BrickInstance
АудиторияПлатформенный инженер, Заказчик (R6)Разработчик

Топология выводится, раскладка хранится

Топология — из spec.connections, как kro строит DAG из ссылок. Позиция — в аннотации ui.cozyap.io/position, отсутствие позиции не ошибка, а повод посчитать раскладку.

ELK layered, не dagre

У узлов типизированные порты на конкретных сторонах. Dagre портов не знает, force-directed читается ужасно. Поток source → build → image → workload → route изначально слоистый.

Типизация — это фича, а не валидация. При перетаскивании из выходного порта гасятся все несовместимые входы. Ошибка типа становится недостижимой, а не сообщаемой.
Редактор · главный риск

Редактор против GitOps

Если приложения раскатываются из git через Flux или Argo — а так устроена каждая Crossplane-платформа из исследования и сам Cozystack — то редактор, применяющий изменения прямо в кластер, пишет в систему, которая их откатит. Пользователь двигает узел, тридцать секунд всё работает, потом исчезает. Это хуже, чем отсутствие редактора.
РежимРедактор пишетКому подходит
Direct applyПрямо в API-серверПриложения без git-апстрима
ProposeОткрывает merge request в репозиторий приложенияGitOps-приложения — норма для прода
EphemeralDry-run оверлей, не сохраняетсяПредпросмотр и исследование

Режим — это свойство приложения (есть ли у него git-апстрим), а не пользовательская настройка. И редактор обязан всегда показывать, в каком он режиме: в propose основная кнопка называется «Предложить изменение», а не «Сохранить».

Порядок

Что делаем и чего не делаем

Порядок сборки редактора

1. Вид приложения только на чтение — авторазметка, живой статус, инспектор. Самое дешёвое, от чего платформа начинает ощущаться настоящей.
2. Редактор заготовок, полная правка, без статуса. Нужен Заказчику для R6 и он проще, чем правка живого.
3. Правка приложений: сначала propose, потом direct.
4. Level-2 плагины узлов — последними.

Не делаем в v1

Динамический fan-out и higher-order кирпичики — ADR-0017 вне скоупа.
Кросс-аппликационный граф — это забота каталога, а не потока данных.
Произвольный пользовательский inline-код по умолчанию.
Realtime-коллаборация — раскладка в аннотациях конфликтует, это принятая цена.
Свободное рисование — каждый элемент канваса обязан соответствовать реальному объекту.
Правка композиций — провал в кирпичик только на чтение.

Собрать 1 и 2 без 3 — связный продукт. Собрать 3 раньше 2 — нет.
Дальше

Решения, которых не хватает

  1. Семантика рендера заготовки. Заготовка разворачивается один раз (отскаффолдили, дальше приложения расходятся) или непрерывно (правка заготовки обновляет все приложения)? «Версионируется Заказчиком» из R6 намекает на второе, первое сильно проще. Это блокирует реализацию.
  2. Владеет ли Application кирпичиками или только выбирает их — нужен ли reclaimPolicy, чтобы удаление приложения удаляло части.
  3. Где исполняется авторизационная часть connection, когда продюсер и консьюмер на разных таргетах.
  4. Версионирование типов портов — добавление поля в sql это релиз платформы, затрагивающий все кирпичики, которые его отдают.
  5. Разрешение конфликта traits — два trait'а правят один pod spec.
  6. Registry и retention (дыра G3) и формат выгрузки в тарификацию (дыра G2) — вопросы к Заказчику, блокируют R4 и R7.
Первый пункт — самый дорогой. Непрерывный рендер заготовок означает, что Заказчик может сломать все приложения одним коммитом в каталог, и под это нужна отдельная модель совместимости и раскатки.
