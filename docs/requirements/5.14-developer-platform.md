# Requirement 5.14 — Developer Platform

## Status

Customer requirement. Source of truth for v1 scope. Received 2026-09-07.

This document records the customer-supplied requirement verbatim (appendix),
its working English form, and — most importantly — the **scope delta** between
what the requirement asks for and what the ADR-0008…0017 series designs.

## Summary

The service moves the customer's work from the infrastructure level to the
application level. A developer uploads source code and describes the
application: which dependencies it needs — database, cache, queue, object
storage — and which runtime parameters. The platform does the rest: builds the
application from source without the developer writing build scripts, creates
and configures the declared dependencies, passes connection parameters to the
application, and publishes it with an address. The developer needs no knowledge
of Kubernetes and never touches manifests.

## Requirement items

| # | Requirement | Primary mechanism |
| --- | --- | --- |
| R1 | Fetch source from the customer's repository and build the application automatically | kpack (Cloud Native Buildpacks) |
| R2 | Declare infrastructure dependencies in the application description; platform creates and connects them | Cozystack managed applications, rendered from `Application` |
| R3 | Automatically pass connection parameters to the application, no manual copying of passwords and addresses | Secret projection (Service Binding shape) |
| R4 | Publish with an address; update on source change; roll back to a previous version; stop and delete | Ingress + cert-manager + external-dns; revisions (see gap G1) |
| R5 | Attach observability and secret storage to the application by default | Cozystack monitoring stack + Vault/OpenBao, injected at render time |
| R6 | Catalog of typical applications and blueprints, extended and versioned **by the Customer** | Bundle format (ADR-0020), blueprint catalog (ADR-0016) |
| R7 | Account for consumption of applications and their dependencies in the project's overall billing | See gap G2 |

## Scope delta against the ADR-0008 series

The requirement is substantially narrower than the platform designed in
ADR-0008…0017. The dependency set is **closed** (database, cache, queue,
object storage) and every member already exists as a Cozystack managed
application. A general-purpose composition engine is not required by any item
of the requirement.

### Out of scope for v1

| ADR / concept | Reason |
| --- | --- |
| ADR-0017 — programmable generators, dynamic fan-out, higher-order `CreateApplication` | Not referenced by any requirement item |
| `execution.mode: stateful` (author-written mini-controllers) | Not needed; source-change triggering is covered by webhooks and kpack |
| Two placement axes, credential bridging, host scheduler (ADR-0015) | Removed by the single-plane model of ADR-0018 |
| Graph builder UI with typed ports and cycle detection | R2 asks for a form ("which dependencies"), not a graph editor |
| Community (AUR-style) catalog | R6 states the catalog is curated and versioned by the Customer |
| Temporal as execution layer (ADR-0010) | Rejected; see ADR-0018 |
| Aggregated API server + PostgreSQL for the catalog | Over-engineered for a curated catalog of tens of blueprints |

### Kept, reduced

- **Typed ports (ADR-0009)** survive only as the narrow core↔dependency
  contract defined in ADR-0019: readiness plus a connection Secret reference.
- **Networking primitives (ADR-0007)** survive unchanged for R4.
- **Catalog versioning (ADR-0016)** survives, reshaped by the bundle format in
  ADR-0020.

## Gaps — requirements with no design coverage yet

- **G1 — Rollback.** The reactive "desired equals actual" model has no concept
  of history, so R4's rollback is not derivable from it. An explicit revision
  object (image digest + values + blueprint version, snapshotted per successful
  deployment) must be part of the `Application` CRD from the start; revisions
  cannot be retrofitted.
- **G2 — Consumption accounting and billing.** Not mentioned anywhere in
  ADR-0008…0017. Requires attributing the consumption of an application **and
  its dependencies** to a project and exporting it to the billing system.
  Dependencies are separate Cozystack applications in their own namespaces, so
  the ownership link must be recorded deliberately. Open sub-question: who pays
  for the platform instance overhead itself (see ADR-0018).
- **G3 — Container registry.** The requirement is silent, but a build produces
  an image that must be stored with per-project isolation and a retention
  policy. Without retention guarantees, R4's rollback breaks once an old image
  is garbage-collected.

## Open questions for the Customer

1. **Registry** — whose, where, what retention policy. Blocks R4 (rollback).
2. **Consumption accounting** — is there an existing billing system, in what
   format does it ingest data, and at what granularity (project, application,
   dependency)?
3. **Rollback semantics** — code/image only, or configuration and dependency
   set as well? Database migrations are not reversible in the general case and
   must be excluded explicitly.
4. **Project boundary** — does "project" map one-to-one onto a Cozystack
   tenant? Determines whether the child-tenant model of ADR-0018 is needed.

## Appendix — original text

Preserved verbatim, in the language it was received, to avoid translation
drift in a contractual requirement.

> **5.14. Платформа для разработчиков**
>
> Услуга смещает работу клиента с уровня инфраструктуры на уровень приложения.
> Разработчик загружает исходный код и описывает приложение: какие ему нужны
> зависимости — база данных, кеш, очередь, объектное хранилище — и какие
> параметры запуска. Дальше платформа делает всё сама: собирает приложение из
> исходного кода без написания сценариев сборки, создаёт и настраивает
> заявленные зависимости, передаёт приложению параметры подключения к ним и
> запускает его, выдав адрес для обращения. Разработчику не требуется знание
> Kubernetes и работа с манифестами.
>
> Состав требований:
>
> - Загрузка исходного кода из репозитория клиента и автоматическая сборка приложения.
> - Объявление инфраструктурных зависимостей в описании приложения; создание и подключение их платформой без участия разработчика.
> - Автоматическая передача приложению параметров подключения к зависимостям, без ручного переноса паролей и адресов.
> - Публикация приложения с выдачей адреса, обновление при изменении исходного кода, откат к предыдущей версии, остановка и удаление.
> - Подключение наблюдаемости и хранения секретов к приложению по умолчанию.
> - Каталог типовых приложений и заготовок, пополняемый и версионируемый Заказчиком, для быстрого старта.
> - Учёт потребления приложений и их зависимостей в общей тарификации проекта.
